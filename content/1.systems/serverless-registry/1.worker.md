The Worker is the registry itself. It serves the native read protocols of the package managers, the
publishing and administration API (`/api/v1`) and a landing page with an admin panel. Files are kept in
[CloudFlare R2](https://developers.cloudflare.com/r2/){:target="_blank"}, credentials in
[CloudFlare KV](https://developers.cloudflare.com/kv/){:target="_blank"}.

## Deployment

Pick one of three ways, all using the same repository:

| Path | For whom | Deploys on |
| --- | --- | --- |
| *Deploy to CloudFlare* button | most installations | every push to your `main` |
| Fork + GitHub Actions | those who prefer GitHub Actions | every push to your fork's `main` |
| Local `npm run deploy` | developers and one-off installs | every time you run it |

Everything is provisioned from `wrangler.jsonc` on the first deploy: the Worker `serverless-registry`,
a KV namespace (`AUTH`), an R2 bucket (`R2_BUCKET`), static assets and an hourly cron cleanup.
Nothing installation-specific is committed - settings live in the CloudFlare dashboard, so updates are conflict-free.

The repository also brings two GitHub workflows for your own copy (see [Updating](#updating)):
**Update from upstream** and **Configure bindings**.

## Configuration

Set in the Worker's *Settings* → *Variables and Secrets*:

| Variable | Type | Description |
| --- | --- | --- |
| `PUBLIC_URL` | variable | Public address of the registry (also the audience of OIDC tokens). |
| `S3_ENDPOINT` | variable | R2 S3 endpoint used for presigned URLs. |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | secrets | R2 API token scoped to the bucket. |
| `SESSION_SECRET` | secret | Signs panel sessions (`openssl rand -base64 48`). |

Optional variables (defaults apply while unset):

| Variable | Default | Effect |
| --- | --- | --- |
| `ECOSYSTEMS` | `composer,npm,cargo,generic,nuget,swift,maven` | Enabled ecosystems; a disabled one answers `404`. |
| `MAX_UPLOAD_BYTES` | `536870912` (512 MiB) | Largest accepted file of a version. |
| `APPEND_WINDOW_HOURS` | `24` | How long files may be appended to a generic version. |
| `TOKEN_PREFIX` | empty | Fixed prefix (e.g. `srg_`) for issued tokens, so leaked ones can be found with grep. |
| `LOGIN_TOKEN_EXTENDED_TTL_HOURS` | `24` | How long a pull token lasts when it is approved with "extended validity" (1 to 720); otherwise one hour. |
| `MAX_PUBLISH_SCOPES` | `20` | Most package versions one publish login token can approve (1 to 100). |
| `CHECK_UPDATES` | `true` | Settings page checks GitHub for a newer release once a day. |
| `R2_BUCKET_NAME` | `serverless-registry` | Bucket name in presigned URLs. |

## Authentication

Every credential is a project name with one or more **roles**, a list of grants for each role and one or more secrets:

- `read` - installs packages; its key token is safe to commit into the consumer's repository (`auth.json`, `.npmrc`, ...),
- `publish` - publishes versions with `sreg`, usually from GitHub Actions; a token that only publishes never reads,
- `admin` - the panel and the administrative API (including yank and delete); no grants of its own, it sees every package.

Roles can be combined in one credential, so that one project installs and publishes (`read` + `publish`, each with its own grants)
or an administrator can also install or publish. A grant is an ecosystem, a package name or `vendor/*` pattern and a version
constraint in that ecosystem's syntax (`*` for all). `read` grants are transitive by default. Grants can be edited as rows or
as text, one per line in the shorthand `eco:package[:versions[:transitive]]`.

A credential holds one or more **secrets**, each with an optional description:

| Secret | What it is |
| --- | --- |
| `key` | A generated token `<project>:<secret>`, used as Bearer, Basic or raw `Authorization` header. A `key` is always generated, never a chosen password. |
| `login` | A password and, optionally, a one-time code (TOTP) for an authenticator app. Used to sign in to the panel and to approve CLI operations in the browser (below). |
| `gh` | Trusts a GitHub repository (optionally a ref, workflow and environment) so its Actions jobs authenticate with OIDC, with no stored secret. |

With several roles, every secret has a **scope**: the roles it may use. The `key` you commit into a repository can stay
`read`-only while the release workflow's `gh` secret is `publish`-only, and only a secret scoped to `admin` administers. Adding a role
later never widens the secrets the credential already has - they keep the roles they had, and new secrets choose their scope.

![Roles of a credential](/systems/serverless-registry/panel-credential-grants.png)

A `gh` secret scoped to `publish` is the recommended setup for CI. The registry picks the credential by the role the request needs,
so one repository can install and publish with OIDC. See the
[deployment guide](https://github.com/kduma-OSS/serverless-registry-worker/blob/main/docs/deployment.md#a-publish-credential-for-github-actions-oidc-no-secret){:target="_blank"}.

### Logins for people

Any credential can hold a `login` secret, so that people use the CLI instead of copying tokens around:
[`sreg login`](/systems/serverless-registry/sreg-cli#sreg-login) and the `--login` option open a page of the registry
(`/authorize/...`), where you sign in (or, when the browser is already signed in, only approve) and the CLI receives a
short-lived signed token:

- a **pull token** lasts one hour, or `LOGIN_TOKEN_EXTENDED_TTL_HOURS` hours when you tick "extended validity",
- a **publish token** lasts 15 minutes and works only for the package versions you approved (at most `MAX_PUBLISH_SCOPES` of them); it is issued only when the
  credential's grants allow every one of them, and with a one-time code a recent one is required,
- an **admin token** for a [yank or delete](/systems/serverless-registry/sreg-cli#sreg-yank) lasts 15 minutes and may only perform exactly the operations you approved.

Expiring the login secret ends its tokens and browser sessions. The Worker does not limit sign-in attempts - add a
CloudFlare rate limiting rule for the path starting with `/authorize/`.

## Admin panel

Opening the registry in a browser shows a small panel, rendered by the Worker without any framework or external resources.

### First run

While the registry has no credential at all, the page first checks the installation settings and lists any missing ones
(with how to add them), then offers to create the first admin. Enter a project name, optionally choose a password
(otherwise one is generated) and tick **Require a one-time code** to protect the login with an authenticator app.

![First run](/systems/serverless-registry/panel-first-run.png)

The password is shown **only once**, together with a QR code (and a link and a key) for the authenticator app when you
asked for the code. Store it in a password manager. The form never appears again, and there is no password reset - consider
creating a second admin credential for a colleague.

![Admin created](/systems/serverless-registry/panel-admin-created.png)

### Login

The login page defaults to a login (the project name) and a password; **Token** is the other tab, for a `key` secret.
With a one-time code the sign-in has two steps: the password, then the code from the authenticator app.
A signed session cookie keeps you signed in for 12 hours.

![Login](/systems/serverless-registry/panel-login.png)

![One-time code](/systems/serverless-registry/panel-login-code.png)

### Approving CLI operations

When a CLI command runs with `--login` (or `sreg login`), the page it prints shows exactly what is requested -
a pull token, a publish token for named package versions, or an admin token to yank or delete them. Sign in with a `login` secret,
or just approve when you are already signed in:

![Sign in to approve a CLI operation](/systems/serverless-registry/panel-authorize-signin.png)

![Approve a publish token for one version](/systems/serverless-registry/panel-authorize-approve.png)

A delete is shown with a warning, and an `admin` credential with a one-time code needs a fresh code to approve it:

![Approve a delete](/systems/serverless-registry/panel-authorize-delete.png)

### Browsing packages (`read` credentials)

A `read` credential sees every package its grants cover, with an ecosystem badge, the number of versions and the latest version.
When the admin has organised the packages into [groups](#package-groups), the list is split into collapsible sections ("Ungrouped" first, then the groups with their subgroups and the number of packages in each).
A filter bar narrows the list by name, group and ecosystem (the group and ecosystem selectors take several choices at once).

![Packages visible to a read credential](/systems/serverless-registry/panel-packages-read.png)

A package page lists its versions and has ready-to-paste client configuration with copy buttons
(a command, files or environment variables - pick one with the chooser). Replace `<token>` with your token.

![Package page with client configuration](/systems/serverless-registry/panel-package.png)

A version page lists its files with sizes and checksums, downloads them through a short-lived presigned link
and shows how to install exactly that version.

![Version page](/systems/serverless-registry/panel-version.png)

### Administration (`admin` credentials)

An admin gets three pages in the header.

**Packages** - the same list, grouped like the consumers' one but also showing empty groups, with *Reindex* and *Delete* on each row; a package's page also lets you yank or delete its versions and move the package to another group. The same operations are available from the CLI with [`sreg yank` and `sreg delete`](/systems/serverless-registry/sreg-cli#sreg-yank).

![Packages (admin)](/systems/serverless-registry/panel-admin-packages.png)

![Package page with its group](/systems/serverless-registry/panel-package-admin.png)

#### Package groups

Groups organise the package list in the panel and on the home page of `read` credentials, and nothing else: they change nothing about access, indexes,
the package managers' protocols or the API. A package is in at most one group (or "Ungrouped"), and groups nest up to five levels deep.

- **Organize** on the *Packages* page puts a checkbox on every row: check any number of packages, then move them to a group, to Ungrouped or to a new group (named on the spot, inside any group).
- **Manage groups** opens a page where you create, rename, move and delete groups as a tree. Deleting a group moves its packages and subgroups up one level.
- Each group is shown as **visible**, **collapsed** (closed in the list until opened) or **hidden**. A hidden group is left out of the lists, with its subgroups and every package in them,
  for admins and `read` credentials alike; admins bring hidden groups back with **Show hidden groups** on the *Packages* page. Hiding only tidies the lists - the packages stay installable and their pages work.

![Organize mode](/systems/serverless-registry/panel-packages-organize.png)

![Managing groups](/systems/serverless-registry/panel-package-groups.png)

**Credentials** - every project in a table, plus a *New credential* form where you choose the roles, the first secret and the grants of each role. A new token or password is shown once.

![Credentials](/systems/serverless-registry/panel-admin-credentials.png)

![New credential](/systems/serverless-registry/panel-new-credential.png)

A credential has the tabs *Overview*, *Grants*, *Secrets* and *Danger zone*. The *Grants* tab has the read and publish grants (an ecosystem, a package name or
`vendor/*` pattern and a version constraint in that ecosystem's syntax; *Edit as text* shows them one per line to copy and paste in bulk) and the three role switches shown above.

![Credential grants](/systems/serverless-registry/panel-credential-grants.png)

Secrets are `key` tokens, `login` passwords (with an optional one-time code) or GitHub Actions `gh` entries (OIDC) that trust a repository, optionally restricted to a ref, workflow or environment. Each can have a description and a scope (the roles it may use), be edited and be expired individually. A new secret's token or password is shown once:

![Credential secrets](/systems/serverless-registry/panel-credential-secrets.png)

**Settings** - the running version, a setup checklist with every installation setting as *Set*, *Missing* or *Default* (secret values are never shown) and, unless `CHECK_UPDATES` is `false`, whether a newer release exists. While one exists, admins also see an **Update available** flag in the header of every page.

![Settings](/systems/serverless-registry/panel-settings.png)

## Updating

The Settings page and the **Update available** flag tell you when a newer release exists. The easiest way to update is the
**Update from upstream** workflow of your own repository (*Actions* tab):

| Input | Meaning |
| --- | --- |
| `channel` | `stable` (newest release), `prerelease` (betas included), `custom` (a tag) or `develop` (upstream's `main`). |
| `tag` | Only for `custom`: a release tag such as `v0.2.0`. |
| `dry_run` | Show the change in the run's summary without pushing. |

It never goes to an older version than your repository has, keeps your own bindings, name, routes and variables when
`wrangler.jsonc` conflicts, checks the result with `wrangler deploy --dry-run` and pushes to the default branch, which deploys.
Files of `.github/workflows` are updated only when you save a token as the repository secret `UPDATE_TOKEN`.

The **Configure bindings** workflow writes the R2 bucket (including its `jurisdiction`: `eu`, `fedramp` or `none`),
KV namespace, Worker name and custom domain into `wrangler.jsonc` from a form, so that deploys and updates keep them.
A bucket created in a jurisdiction needs it in the binding, otherwise a deploy binds the Worker to another, empty bucket.

Read the changelog before updating: entries marked **Breaking** need something from you and **Requires migration** entries run
automatically on the first request after the deploy. Details, manual update paths and rollback are in the
[deployment guide](https://github.com/kduma-OSS/serverless-registry-worker/blob/main/docs/deployment.md#7-updating){:target="_blank"}.

### Protection against a wrong R2 bucket

The Worker remembers an installation id in KV and in the bucket. When a deploy binds it to another or a new bucket, the
package and publish endpoints answer `503 bucket_mismatch` instead of working on the wrong bucket (nothing is published into
it, nothing looks deleted), and the panel shows a banner. Fix the binding and deploy again; only if the bucket really is the
new one, an admin confirms it with **Use this bucket**. See
[troubleshooting](https://github.com/kduma-OSS/serverless-registry-worker/blob/main/docs/deployment.md#10-troubleshooting){:target="_blank"}.

## Compatibility

The Worker and `sreg` are released independently. The Worker answers with the oldest accepted client in
`X-Min-Client-Version` and rejects older ones with `426` (`sreg` exit code `3`). The previous API version is kept
for at least one minor release after an incompatible change.
